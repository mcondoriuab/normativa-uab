# FE-005: Estados: cargando, error y rechazo

## Contexto

Con el LLM real, una respuesta puede tardar varios segundos, el servidor puede
fallar y el sistema puede rechazar la pregunta a propósito. Cada caso debe verse
distinto para que el usuario entienda qué pasa.

## Objetivo

Que la interfaz muestre claramente cuatro estados: cargando, respuesta, rechazo
y error.

## Entradas

- `apps/web/app.js`, `apps/web/estilos.css`
- `docs/ARQUITECTURA.md` (`rechazada`, HTTP 422)
- El mock de BE-002 (la palabra `rechazo` provoca un rechazo)

## Pasos sugeridos

1. **Cargando:** desactiva el botón, cambia su texto a "Buscando…" y muéstralo
   hasta que llegue la respuesta o el error.
2. **Rechazo** (`rechazada: true`): muestra la respuesta con un estilo neutro,
   no de error, y la sugerencia de consultar a secretaría. Sin citas.
3. **Error:** si `fetch` falla o el estado HTTP no es 200, muestra un mensaje
   comprensible ("No se pudo obtener respuesta. Inténtalo de nuevo.") en lugar
   del error técnico.
4. **Servidor despertando:** en el plan gratuito de Render, la primera petición
   tras un rato sin uso tarda hasta un minuto. Si la respuesta tarda más de 5
   segundos, añade al estado de carga: "El servidor está despertando, puede
   tardar hasta un minuto."
5. Vuelve a activar el botón en todos los casos (`finally`).

## Fuera de alcance

- Reintentos automáticos o *timeouts* configurables.

## Criterios de aceptación

- [ ] Durante la petición no se puede enviar otra.
- [ ] Si tarda más de 5 s, aparece el aviso de servidor despertando.
- [ ] Una pregunta con la palabra `rechazo` muestra el estado de rechazo.
- [ ] Con la API apagada, se ve el mensaje de error y el botón vuelve a
      funcionar.

## Cómo verificar

Probar los tres casos en el navegador; para el error, parar `uvicorn` y
preguntar. Adjuntar capturas al PR.

## Entregables

- `apps/web/app.js`
- `apps/web/estilos.css`

## Para aprender

Estados de interfaz, manejo de errores con `try/catch/finally`, por qué un
rechazo no es un error.
