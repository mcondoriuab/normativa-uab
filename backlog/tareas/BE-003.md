# BE-003: Motor real en la API: carga al arrancar y registro anónimo

## Contexto

La web ya funciona contra el mock de BE-002. Como `responder()` (IA-016)
devuelve la misma forma que el contrato, conectar el motor real debería ser
cambiar muy pocas líneas. Si hace falta cambiar mucho, algo del contrato no se
respetó.

Leer todos los fragmentos de Supabase y construir el índice BM25 tarda unos
segundos. Si se hace en la primera pregunta, el primer usuario espera mucho más
que el resto, así que se hace **al arrancar el servidor**.

Saber qué pregunta la gente de verdad sirve para ampliar el golden set y
encontrar fallos. Pero las preguntas sobre normativa son sensibles
(`docs/ETICA.md`): se guardan **sin nada que identifique** a quien pregunta, y
se avisa en la interfaz.

Es una tarea del **camino crítico**: BE-007 la despliega el 17 de noviembre.
Puedes hacer la Parte 3 (registro de consultas) en cuanto BE-008 esté cerrada,
antes de que exista `responder()`.

Esta tarea junta las antiguas BE-003 (conectar `/preguntar` al motor real),
BE-004 (cargar el índice una sola vez) y BE-010 (registro anónimo de
consultas).

## Objetivo

Que `POST /preguntar` responda con `ia.responder.responder`, que la API cargue
fragmentos e índice al arrancar, y que cada consulta se guarde de forma anónima
en la tabla `consultas` sin que un fallo al guardar rompa la respuesta.

## Entradas

- `apps/api/main.py` (BE-002 y BE-008)
- `ia/responder.py` (IA-016), `ia/hibrida.py` (función `cargar`, IA-007)
- `ia/db.py` (BE-008)
- `docs/ARQUITECTURA.md` (tabla `consultas`), `docs/ETICA.md`
- `apps/web/index.html`
- Documentación oficial de FastAPI sobre `lifespan`

## Pasos

### Parte 1: conectar el motor real

1. En `apps/api/main.py`, importa `responder` de `ia.responder` y llámalo
   dentro de la ruta con `peticion.pregunta`. Devuelve lo que devuelve.
2. Borra el código del mock, incluido el caso especial de la palabra `rechazo`.
3. Rodea la llamada con `try/except Exception`. Si `responder` lanza una
   excepción (por ejemplo, el LLM no responde), registra el error con
   `logging.exception(...)` y devuelve **HTTP 503** con un mensaje genérico
   (`raise HTTPException(status_code=503, detail="El asistente no está disponible. Inténtalo más tarde.")`).
   Nunca devuelvas el error interno al usuario.

### Parte 2: cargar el índice al arrancar

4. Usa el mecanismo `lifespan` de FastAPI (consulta su documentación actual):
   una función `async` con `@asynccontextmanager` que se pasa a
   `FastAPI(lifespan=...)`.
5. Dentro, antes del `yield`, llama a `ia.hibrida.cargar()` y registra en el
   log cuánto tardó (`time.perf_counter()` antes y después).
6. Mide con `time curl ...` la primera y la segunda pregunta, antes y después
   del cambio, y anota los cuatro tiempos en el PR.

### Parte 3: registro anónimo de consultas

7. Añade a `ia/db.py`:

   ```python
   def guardar_consulta(pregunta: str, rechazada: bool, ids_citados: list[str], latencia_ms: int) -> None:
   ```

   Con un `insert` con parámetros (`%s`), nunca concatenando texto.
8. En `/preguntar`, mide la latencia (`time.perf_counter()`) y, después de
   obtener la respuesta, llama a `guardar_consulta`. Los `ids_citados` son
   `f"{c['documento']}#art-{c['articulo']}"` de cada cita, o
   `f"{c['documento']}"` si `articulo` es `None`.
9. Rodea `guardar_consulta` con su propio `try/except`: **si guardar falla, el
   usuario igual recibe su respuesta**. Registra el error en el log y sigue.
10. No guardes IP, *user-agent*, cookies ni ningún otro dato de la petición.
11. En `apps/web/index.html`, junto al aviso legal, añade:
    `Las preguntas se guardan de forma anónima para mejorar el asistente.`

## Fuera de alcance

- Cachés de respuestas o varios procesos.
- El arranque en frío de Render (el servidor dormido): no se arregla aquí.
- Paneles o informes sobre las consultas y borrado automático de registros.

## Criterios de aceptación

- [ ] Una pregunta del golden set devuelve una respuesta real con citas reales.
- [ ] No queda código del mock.
- [ ] Con el LLM mal configurado (borra `LLM_API_KEY` de tu `.env` para
      probarlo), la API responde 503 y no se cae.
- [ ] El log de arranque indica que el índice se cargó y cuánto tardó, y la
      primera pregunta ya no es notablemente más lenta que la segunda.
- [ ] Cada pregunta crea una fila en `consultas` con los campos del contrato y
      ningún dato de la persona.
- [ ] Con la base caída (pon una `DATABASE_URL` incorrecta después de
      arrancar), `/preguntar` sigue respondiendo.
- [ ] El aviso de registro anónimo aparece en la web y la web funciona sin
      otros cambios.

## Cómo verificar

```bash
uvicorn apps.api.main:app
time curl -s -X POST localhost:8000/preguntar -H 'Content-Type: application/json' \
     -d '{"pregunta": "<pregunta del golden set>"}'
python -c "
from ia.db import conectar
with conectar() as c:
    print(c.execute('select * from consultas order by id desc limit 1').fetchone())
"
```

## Para aprender

Por qué los contratos permiten sustituir piezas; errores internos frente a
mensajes al usuario. Ciclo de vida de un servidor y latencia de arranque.
Privacidad por diseño, minimización de datos y fallos que no deben romper la
respuesta principal.

## Notas de cierre

### Qué aprendí

Conecté `/preguntar` con `ia.responder.responder` conservando el contrato de
la API. Por eso la web puede mostrar una respuesta real y sus citas sin
cambiar su JavaScript. Eliminé las respuestas simuladas y la regla especial
que rechazaba una pregunta por contener la palabra `rechazo`.

Usé `lifespan` con `asynccontextmanager`: el código anterior al `yield` carga
los fragmentos y crea BM25 antes de aceptar la primera petición. Registré el
tiempo de carga con `time.perf_counter()`.

Separé dos tipos de fallo. Si falla el motor, devuelvo 503 con un mensaje
genérico y registro la excepción. Si falla el guardado, conservo la respuesta
que ya se generó y registro el error por separado.

Guardé solo pregunta, rechazo, ids citados y latencia del motor. El id de la
fila y su fecha los genera Postgres. No añadí IP, user-agent, cookies ni datos
de identidad al registro. Añadí el aviso de registro anónimo junto al aviso
legal de la web.

### Cómo lo comprobé

Probé la API con Supabase, Voyage y Groq reales. Pregunté «¿Qué porcentaje de
asistencia regular a clases se valora en la evaluación?» y obtuve una respuesta
que indica el 80 % con una cita del artículo 19. Contrasté el texto y la página
de las citas con los fragmentos de Supabase.

Medí con `curl.exe` la primera y la segunda pregunta en dos arranques del
mismo endpoint real. Para la fase anterior desactivé la precarga únicamente
en el proceso de prueba; mantuve el motor real y el registro. En la fase
posterior usé el `lifespan` de la implementación. Reinicié el estado del índice
entre fases. No comparé una respuesta simulada con una respuesta real.

| Escenario | Primera pregunta | Segunda pregunta |
|---|---|---|
| Motor real con carga perezosa | 10.913654 s | 6.510172 s |
| Motor real con precarga | 6.236937 s | 49.646487 s |

La segunda pregunta posterior tuvo dos esperas de 20 segundos por la cuota
de Voyage. Conservo ese dato y no lo atribuyo al índice. Esta pareja de
mediciones no demuestra una mejora de la latencia media del proveedor.

Comprobé por separado que la carga se hacía una vez por arranque: antes de
la precarga se ejecutaba durante la primera pregunta; después ya estaba hecha
antes de recibirla. El log de esa medición indicó:

```text
Índice BM25 cargado en 2.433 segundos.
```

Las cuatro peticiones devolvieron 200 y generaron cuatro filas anónimas.
También probé un rechazo real para el horario de biblioteca: devolvió 200,
`rechazada: true` y citas vacías, y guardó una fila con `ids_citados: []`.

Ejecuté `python -m uvicorn apps.api.main:app` en el puerto 8000, envié otra
pregunta con `curl.exe` y consulté la última fila de `consultas`. El log mostró
la carga en 2.658 segundos; la petición devolvió 200 en 7.393785 segundos y
guardó el id citado `reglamento-estudiantil-2016#art-19`.

Con pruebas controladas verifiqué los ids de citas con y sin artículo, los
cuatro parámetros del INSERT, el rechazo con ids vacíos, la ausencia de una
regla especial para `rechazo`, los errores 422 y 503, la carga única y que se
sirven la página, JavaScript y CSS con el aviso anónimo. Las comprobaciones de
sintaxis, dependencias y `git diff --check` pasaron.

### Qué falló y qué queda para revisión

Al principio `TestClient` quedó bloqueado en el socket interno de asyncio
dentro del entorno restringido de Windows. Repetí las pruebas con permiso de
red local y pasaron. Una comprobación del proceso de prueba esperaba el nombre
`OperationalError`, pero psycopg produjo `ConnectionTimeout`; corregí esa
comprobación sin cambiar el comportamiento de la API.

Probé un destino de base incorrecto solo durante el guardado: se produjo un
error real de conexión, quedó registrado y el usuario recibió su respuesta
real con HTTP 200. También probé la clave del LLM ausente en la configuración
que lee el módulo: obtuve 503 genérico y la web siguió disponible.

Hay una precisión pendiente en el criterio de caída de base: si cambio
`DATABASE_URL` globalmente después del arranque, también falla la búsqueda
vectorial de IA-008. En esa prueba `/preguntar` devolvió 503 genérico,
`/salud` devolvió 503 y la web siguió devolviendo 200. Al restaurar la conexión,
el servidor volvió a responder normalmente.

La tolerancia al fallo aislado del registro está comprobada. Mantener una
respuesta generada cuando cae toda Supabase requeriría otro mecanismo para la
búsqueda; lo dejé señalado para el docente y conservé el alcance de BE-003.
